Project Overview

A reliable bridge from meta-analysis to machine learning

NiMARE is an open-source Python library for performing neuroimaging meta-analysis. It provides tools for coordinate-based and image-based meta-analysis, annotation, decoding, and reproducible workflows built around structured collections of studies and analyses. Its Studyset representation brings together information such as activation coordinates, statistical images, metadata, and annotations.

Although these data are naturally useful for predictive modeling, moving from a NiMARE Studyset to a machine-learning experiment previously required substantial custom code. Researchers had to generate modeled activation maps, convert them into feature matrices, align metadata and prediction targets, preserve study identifiers, design leakage-safe splits, and manually connect the result to scikit-learn.

The goal of this project was to create a consistent bridge between NiMARE and the wider Python machine-learning ecosystem. The resulting interface converts meta-analytic data into a structured, scikit-learn-compatible representation while retaining the scientific context needed for responsible model evaluation.

The workflow is centered on two new abstractions: MAFeatureExtractor, which converts a Studyset into machine-learning features, and MAFeatureDataset, which stores those features together with targets, grouping labels, feature metadata, and provenance. Supporting utilities provide grouped cross-validation, sparse-compatible dimensionality reduction, and direct export to scikit-learn.

Rather than implementing a separate machine-learning framework inside NiMARE, the project gives researchers a reliable path into existing scikit-learn estimators, pipelines, model-selection tools, and evaluation functions.

02

Problem and Motivation

Scientific data needs a scientific data contract

A neuroimaging meta-analytic dataset is not immediately equivalent to a conventional machine-learning table. A single analysis may contain a set of reported coordinates rather than a fixed-length feature vector. Several analyses may originate from the same study, and therefore cannot be treated as statistically independent observations. Metadata and annotations may exist at different levels, use different types, or contain missing values. The resulting brain maps are also extremely high-dimensional.

Before this project, researchers could generate modeled activation maps with NiMARE kernel transformers, but there was no unified interface for turning those maps into an aligned dataset suitable for scikit-learn. Each downstream project had to make its own decisions about row identity, feature order, sparse storage, outcome extraction, and data splitting.

This fragmentation created both engineering overhead and scientific risk.

The most serious risk was data leakage. If two analyses from the same publication were randomly assigned to different folds, the model could learn study-specific characteristics from the training data and encounter closely related information during testing. The resulting evaluation score could appear stronger than the model’s real ability to generalize to unseen studies.

Memory usage presented another challenge. A modeled activation map may contain tens or hundreds of thousands of voxels. Storing one dense map for every analysis can quickly become impractical, even though these maps are often highly sparse. Any general solution therefore needed to preserve sparse representations until a researcher explicitly selected a reduction method.

The interface also needed to handle heterogeneous data without hiding important assumptions. Numeric metadata can be appended directly to a feature matrix, but free text, categorical descriptors, or multi-label annotations require an explicit encoding strategy. Automatically transforming these fields would make the API convenient at the cost of making the scientific workflow less transparent.

The project addressed these problems by defining a clear data contract: one row per retained analysis, stable row alignment, explicit study-level groups, sparse voxelwise features, optional descriptors and targets, and recorded provenance.

03

What I Built

A compact interface with clear responsibilities

MAFeatureDatasetData contract

MAFeatureDataset is the central data container introduced by the project. It stores the feature matrix together with all of the information required to interpret and safely use its rows:

  • analysis identifiers;
  • study identifiers used as grouping labels;
  • map-derived and descriptor-derived features;
  • optional prediction targets;
  • feature names and column boundaries;
  • map-generation and source provenance.

The class validates row and column alignment during construction. Identifiers, study groups, targets, map features, and descriptors must all refer to the same observations and appear in the same order. This catches alignment errors at the boundary of the workflow instead of allowing them to silently affect a later model.

The container also distinguishes map columns from descriptor columns. This is important because voxelwise features and tabular descriptors generally require different preprocessing. A researcher can reduce the map features while passing descriptor columns through unchanged.

Copying and row slicing preserve the complete dataset structure, including targets and provenance. Unreduced voxelwise maps remain sparse, protecting the workflow from accidental memory expansion.

MAFeatureExtractorStudyset conversion

MAFeatureExtractor handles conversion from a NiMARE Studyset to an MAFeatureDataset. It uses an explicitly selected NiMARE kernel transformer to generate modeled activation maps and represents each retained analysis as a row.

The extractor can read selected fields from Studyset metadata or annotations. Numeric fields can become additional descriptor features, while a selected scalar field can become the prediction target. All values are aligned to the original analysis identifiers before rows are retained or removed.

Analyses without coordinates can be handled through an explicit policy. In drop mode, they are excluded and their identifiers are recorded in the dataset provenance. In include mode, they remain in the dataset as all-zero sparse map rows. This makes the treatment of incomplete coordinate data visible and reproducible.

Map generation can also be cached. Repeated experiments with different downstream estimators or reduction parameters do not need to regenerate identical modeled activation maps when the Studyset, mask, coordinates, metadata, and kernel configuration remain unchanged.

to_sklearn()Export

An MAFeatureDataset can be exported through to_sklearn(). The method returns a familiar scikit-learn Bunch containing:

  • data, the aligned feature matrix;
  • target, the optional prediction outcome;
  • groups, the study identifiers;
  • feature_names;
  • map_columns;
  • descriptor_columns.

This design keeps responsibilities clear. The extractor consumes domain-specific NiMARE data and produces a structured dataset; the dataset exports the data it already owns. NiMARE does not train the predictive model itself. Once exported, the result can be used with standard scikit-learn estimators and evaluation utilities.

Grouped splittingEvaluation

MAFeatureDataset.make_cv() constructs cross-validation strategies that are already bound to the dataset’s study groups. It supports grouped folds through GroupKFold and reproducible grouped shuffle splits through GroupShuffleSplit.

Because the grouping information is carried by the dataset, users do not need to manually rebuild it whenever they evaluate a model. The helper also detects cases where the requested number of folds exceeds the number of unique studies and raises a clear error.

Map reductionPreprocessing

The project includes a sparse-compatible truncated singular value decomposition pathway for reducing high-dimensional activation maps. make_preprocessor() creates an unfitted scikit-learn ColumnTransformer that applies reduction only to map columns and passes descriptor columns through unchanged.

Crucially, this preprocessor is designed to be placed inside a scikit-learn pipeline. During cross-validation, the reducer is fitted only on the training fold and then applied to the held-out fold. Dimensionality reduction therefore does not leak information across the evaluation boundary.

Examples and testsValidation

A complete example demonstrates classification of n-back and flanker task analyses from a parquet-backed Studyset. It generates sparse modeled activation features with an MKDAKernel, extracts task labels, performs truncated-SVD reduction, trains logistic regression, and evaluates the pipeline using study-grouped cross-validation.

The implementation is supported by tests covering construction, validation, sparse data preservation, field extraction, target alignment, coordinate-missing policies, caching, copying, grouped cross-validation, reducer behavior, and the end-to-end Studyset conversion path.

The Studyset remains the source of scientific data. MAFeatureExtractor performs domain-specific conversion, including map generation and row alignment. MAFeatureDataset becomes the stable boundary between NiMARE and scikit-learn. From that point onward, standard estimators, pipelines, scoring functions, and model-selection tools can be used.

This separation also makes the system extensible. New map-generation strategies can reuse the same dataset representation, while future reducers can be added without changing how Studysets are converted or how models consume the exported data.

05

Engineering Decisions and Challenges

Designing for trustworthy evaluation

01

Preventing study-level leakage

The most important scientific decision was to treat an analysis as a machine-learning row while treating its parent study as the splitting group. A single study may report several analyses based on overlapping participants, acquisition procedures, or preprocessing decisions. Splitting those analyses independently would violate the assumptions behind held-out evaluation.

The interface therefore carries study_ids alongside every row and uses them in all provided cross-validation helpers. This makes leakage prevention a property of the dataset design instead of an optional convention left to each example.

02

Preserving sparse, high-dimensional maps

Voxelwise activation maps can be large, but most modeled activation values are zero. The implementation uses sparse matrices for unreduced map features and avoids implicit conversion to dense arrays. When descriptor columns are added, they are combined with the maps without densifying the full matrix.

Truncated SVD was selected as the first reduction path because it can operate directly on sparse input. Dense reduced components are acceptable after an explicit transformation because their dimensionality is controlled by the user.

03

Separating conversion from model fitting

MAFeatureExtractor intentionally does not behave like a fitted scikit-learn estimator. It converts a domain-specific Studyset; it does not learn predictive parameters from X and y. Giving it fit() and fit_transform() methods would imply semantics that do not match its role.

Similarly, to_sklearn() belongs to MAFeatureDataset, because export is an operation on an object that already contains the aligned data. The resulting public workflow is explicit:

dataset = extractor.transform(studyset)
bunch = dataset.to_sklearn()

This boundary keeps the API understandable and gives the dataset room to support additional export formats in the future.

04

Maintaining row alignment

Coordinates, maps, metadata, annotations, targets, and identifiers may originate from different tables. Removing an analysis from only one source can shift every subsequent row and quietly corrupt a model.

The implementation constructs retention masks from stable analysis identifiers and applies them consistently to every row-aligned component. Dataset construction then verifies the resulting dimensions. Tests include cases where Studyset table order differs from the apparent identifier order, ensuring that values remain attached to the correct analyses.

05

Handling heterogeneous types explicitly

Metadata and annotations can be numeric, categorical, textual, or multi-label. The interface currently supports direct numeric descriptor extraction and scalar target selection. Unsupported representations are intended to require an explicit transformer rather than being encoded through hidden defaults.

This is both an API decision and a reproducibility decision. Encoding categories, tokenizing abstracts, and defining multi-label outcomes are modeling choices that should be visible in the final pipeline.

06

Avoiding preprocessing leakage

A dimensionality reducer fitted before cross-validation has already observed the held-out data, even when it has not seen the target labels. The project therefore returns an unfitted preprocessor intended for use inside a scikit-learn pipeline. Each fold learns its reduction only from the corresponding training partition.

Future Work

Extensions beyond the current implementation

Future direction

The current implementation establishes the core data contract and an end-to-end sparse modeling workflow. Several extensions can build on this foundation.

The reduction API can be expanded with variance thresholding and atlas-based aggregation, allowing researchers to choose between voxel-level components and anatomically interpretable regional features. Text vectorizers and categorical encoders could support abstracts, titles, and richer annotations while preserving explicit control over how those values are transformed. Target transformers could similarly enable structured multi-label prediction tasks.

Further work could add benchmarking on large Studysets, richer missing-data diagnostics, feature-name propagation after reduction, and more examples covering regression, multimodal descriptors, and model interpretation. The interface could also support additional machine-learning ecosystems while retaining MAFeatureDataset as the shared representation.
